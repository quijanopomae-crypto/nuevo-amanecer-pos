## Objetivo
Permitir que una venta se registre correctamente aunque no haya internet.

Flujo obligatorio:

POS/Android
-> persistencia local durable
-> OUTBOX
-> POST /commands/sale.create
-> D1

La venta nunca debe depender de que la red esté disponible en el momento de confirmar.

## Reglas obligatorias
1. Persistir localmente antes de intentar enviar.
2. Cada venta usa un operation_id estable.
3. Los reintentos usan exactamente el mismo operation_id.
4. Nunca crear un operation_id nuevo para un retry.
5. La pérdida del ACK no puede duplicar venta, inventario ni caja.
6. Recarga/cierre de navegador no puede perder una venta PENDING.
7. El OUTBOX debe sobrevivir offline y reload.
8. Al volver internet debe reintentar de forma segura.
9. Integrar con A3 sale.create.
10. No usar SENT como estado financiero final.

## Estados
Usar estados equivalentes a:

- PENDING
- ACKED
- REJECTED
- NEEDS_REVIEW

PENDING:
guardado localmente y pendiente de confirmación cloud.

ACKED:
A3 confirmó created o already_processed.

REJECTED:
servidor rechazó definitivamente la operación y no debe entrar en retry infinito.

NEEDS_REVIEW:
estado ambiguo o conflicto que requiere revisión; no aplicar efectos financieros adicionales.

## Lost ACK
Caso obligatorio:

1. sale.create procesa correctamente.
2. respuesta se pierde antes de llegar al cliente.
3. cliente conserva PENDING.
4. retry usa mismo operation_id.
5. servidor devuelve already_processed.
6. cliente cambia a ACKED.
7. cero duplicados.

## Fallos de red
- offline -> conservar PENDING
- timeout -> conservar PENDING
- error 5xx -> conservar PENDING y permitir retry
- auth inválida/revoked/read_only -> no retry infinito
- operation_id conflict -> NEEDS_REVIEW o rechazo seguro
- payload local no puede mutar silenciosamente entre retries

## Integridad
El payload financiero pendiente debe quedar protegido contra mutaciones accidentales.

Conservar lo necesario para demostrar que un retry corresponde a la misma intención financiera enviada originalmente.
