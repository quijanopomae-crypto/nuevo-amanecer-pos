# V1.2 — Operación y recuperación

Procedimiento del release `v1.2-production`, aprobado en `V1.2_STATUS.md` con la
confirmación del propietario sobre la caja real, el respaldo y el teléfono Android.
Conservar el ZIP, su archivo `.sha256` y `V1.2_RELEASE_REPORT.json` juntos.

## Operación

Usar un PC principal y una sola pestaña de escritura. Conservar el paquete completo,
ejecutar `INICIAR_POS.cmd` y abrir `http://127.0.0.1:8788/POS/index.html` en el perfil
habitual. Node.js está instalado en la PC de preparación. La apertura directa por
`file://` no permite OCR. Antes de cambiar el origen de una caja existente, exportar
su respaldo e importarlo en el nuevo origen; ver `V1.2_USO.md`.
La venta local y el OUTBOX no requieren que la
nube esté disponible. No borrar almacenamiento del navegador ni cambiar de perfil
sin exportar y comprobar antes un respaldo.

El lector abre `https://nuevo-amanecer-sync-lab.nuevo-amanecer-pos.workers.dev/read-only.html`.
Como alternativa recibe únicamente `POS/read-only.html` y `POS/js/sync/read-only.js`,
conservando las rutas relativas, más su clave de lectura por un canal seguro.
No entregar al lector SYNC_TOKEN ni el token administrativo de Cloudflare.

## Respaldo de datos

Desde la caja principal, exportar el respaldo completo mediante la función
existente del POS. Guardarlo en una segunda ubicación. El respaldo incluye datos
V9 y OUTBOX, con integridad SHA-256; no incluye las credenciales cloud.
Las pruebas en perfiles aislados no constituyen una copia de los datos comerciales
que tenga abiertos el propietario en otro navegador.

## Recuperar la aplicación y los datos

1. Verificar el SHA-256 del ZIP contra `V1.2_RELEASE_REPORT.json` y el archivo `.sha256`.
2. Extraer el paquete completo en una carpeta estable; conservar el orden de scripts.
3. Abrir un único POS escritor en el perfil elegido. No abrir dos copias para escribir.
4. Importar el respaldo completo desde la función existente. Verificar integridad,
   ventas, caja, créditos, inventario y operaciones pendientes antes de continuar.
5. Abrir `http://127.0.0.1:8788/tools/pos-local/setup.html` en el mismo perfil y
   comprobar/guardar la credencial de escritura vigente del propietario. Cerrar la
   pestaña escritora anterior y volver a abrirla para cargar esa configuración.
   Nunca guardar el valor en HTML/JS, repo, ZIP o reporte.
6. Reconectar. El OUTBOX reutiliza operation_id y hash: un reintento no debe duplicar
   operaciones. Confirmar la recepción y el visor antes de retomar operación normal.

El propietario ya confirmó el respaldo completo
`nuevo_amanecer_backup_completo_2026-09-11.json`. El respaldo contiene datos del
negocio y se conserva por separado; no se incorpora al ZIP del programa. Mantener
la dirección `http://127.0.0.1:8788` y el mismo perfil durante el uso habitual.

Comprobación del archivo en PowerShell, desde la carpeta de entrega:

```powershell
Get-FileHash -Algorithm SHA256 -LiteralPath .\Nuevo_Amanecer_POS_V1.2_Production.zip
```

## Fallos cloud

- Sin red/5xx/Worker no disponible: las operaciones quedan PENDING y reintentan.
- 401: corregir la credencial; usar el reintento explícito existente. No hay bucle de login.
- 409: preservar ambos registros y analizar el conflicto. No reemplazar datos ni forzar
  un reintento que sobrescriba dinero o inventario.
- No rotar SYNC_TOKEN sin actualizar coordinadamente la caja principal.
- Si READ_TOKEN y SYNC_TOKEN son iguales, el gateway cierra ambos accesos.

## Recuperación cloud

Conservar la D1 existente; no borrarla ni recrearla. Las migraciones son acumulativas.
Configurar los dos secretos mediante Wrangler o el dashboard y desplegar el Worker
del release validado. Los secretos no son recuperables desde los archivos fuente.
La copia DPAPI histórica del token de lectura es anterior a la renovación y no debe
utilizarse como credencial vigente. Recuperar las credenciales por el canal seguro
del propietario, sin incluirlas en fuentes, paquetes ni reportes.

Ante un 401 después de actualizar secretos, comparar las versiones y el despliegue
activo antes de tocar credenciales. En el incidente verificado del 11 de septiembre,
las versiones 13/14 estaban subidas pero el tráfico seguía en la 12. La corrección fue
activar la versión 14 existente, no volver a generar tokens ni subir código diferente.

Desde `tools/cloudflare-lab`, instalar las dependencias fijadas con `npm ci`.
Con el token administrativo en el entorno, aplicar las migraciones existentes
con `npm run migrate:remote`, configurar ambos secretos mediante Wrangler y
ejecutar `npm run deploy`. El build copia únicamente los dos archivos del visor
desde POS y rechaza contenido inesperado. Las APIs `/read/*` y `/sync/*` siguen
atendidas por el Worker. No publicar el directorio completo del POS como assets.

## Recuperación de fuentes

El cierre parte del commit `642e90bde2c87fb13663061f506acfa24298080c`; la recuperación
de la sesión final retomó `d26d55f4bf7698237afb51f4a8445e505718081b` en la misma rama.
El SHA definitivo es el commit al que apunta `v1.2-production`, registrado junto al
SHA-256 de `Nuevo_Amanecer_POS_V1.2_Production.zip` en `V1.2_RELEASE_REPORT.json`.
En el repositorio, `git rev-parse 'v1.2-production^{commit}'` debe coincidir con ese SHA.
Para extraer las fuentes sin modificar la caja actual:

```powershell
git archive --format=zip --output=V1.2_fuentes_recuperacion.zip v1.2-production
```

Ese archivo de fuentes es para mantenimiento; el paquete operativo oficial es el
ZIP filtrado por la lista permitida, con su SHA-256 verificado.
Para recuperar sin tocar una caja en uso, extraer el ZIP o el archivo del tag en
una carpeta nueva y seguir el procedimiento de importación anterior.
No sustituir el respaldo de datos comerciales por el código o por datos de ensayo.

## Repetir las verificaciones

Estos comandos requieren el repositorio de desarrollo recuperado desde el commit/tag,
con sus dependencias de pruebas; los tests no forman parte del ZIP operativo.
Desde la raíz del worktree:

```powershell
node --test tests/cloud-sync/read-only.test.mjs
node --test tests/cloud-sync/worker-cors.test.mjs
node --test tests/cloud-sync/outbox-sync.test.mjs
node tests/cloud-sync/rc-browser.mjs
node --test tests/release-local-server.test.mjs
```

El RC necesita Playwright resoluble mediante `PLAYWRIGHT_MODULE` o instalado en el
entorno de pruebas, y Chrome/Edge. Crea y elimina exclusivamente perfiles temporales.

Para el recorrido real, cargar SYNC_TOKEN y READ_TOKEN en el entorno y ejecutar:

```powershell
node tests/cloud-sync/rc-browser.mjs --remote
```

Ese comando crea dos ventas de ensayo identificadas como no comerciales en un
perfil aislado y las envía a la D1 existente. No borra registros posteriores.
La verificación de un segundo perfil que contiene no sustituye el gate físico.

La prueba del paquete preparado también requiere SYNC_TOKEN en el entorno y Playwright:

```powershell
node tests/release-local-browser.mjs RUTA_DE_LA_CARPETA_PREPARADA
```

Usa un contexto de navegador aislado, prueba credenciales mediante GET y ejecuta OCR
real con los recursos del paquete. No configura el perfil comercial ni crea ventas.

Para comprobar el visor HTTPS y el contrato remoto sin crear ventas nuevas:

```powershell
node tests/cloud-sync/hosted-reader.mjs
node tools/cloudflare-lab/test/read-only-remote.test.mjs
node tools/cloudflare-lab/test/remote-release.test.mjs
```

El último reutiliza los UUID de `evidence/v1.2/rc-remote.json`, confirma idempotencia
y un conflicto rechazado. Requiere ambos tokens; no imprime sus valores.
