# V1.3 D1 backup and recovery

## Estado actual — 2026-09-24

Este documento describe la capa de backup/recovery de CANON sin autorizar ningún cambio remoto.

- Código de backup: integrado desde `checkpoint/v1.3-pc-20260923` en Fase 5A.
- Producción: **sin cambios**.
- Deploy del Workflow: **NO ejecutado**.
- Migraciones CANON remotas: **NO ejecutadas**.
- Escritura CANON desde POS: **NO activada**.
- Restore real desde R2 hacia una D1 temporal: **OWNER_ONLY / pendiente de evidencia operacional**.
- El checkpoint original debe conservarse mientras queden bloques REWORK/BLOCKED.

La implementación está restringida a la base CANON `nuevo-amanecer-prod-v2`,
database ID `cf2c83d3-f187-472e-967b-0ad24be969eb`. El ID no es un secreto y
se valida de forma fail-closed para evitar apuntar accidentalmente a otra D1.

## Qué hace el código

`tools/cloudflare-backup/` contiene un Cloudflare Workflow programado para:

1. iniciar un export D1;
2. esperar el bookmark del export;
3. descargar el SQL firmado;
4. rechazar export vacío o mayor a 16 MiB;
5. calcular SHA-256;
6. guardar SQL en R2;
7. releer y verificar tamaño, metadata y hash;
8. escribir un manifest `PASS`;
9. escribir un manifest `FAIL` cuando la operación falla después de iniciarse.

El handler HTTP devuelve 404 y no expone una API pública.

## Secretos requeridos — nunca en Git

Cuando el owner decida desplegar esta capa, el Worker necesita:

- `ACCOUNT_ID`
- `DATABASE_ID`
- `D1_REST_API_TOKEN`

El token debe tener únicamente los permisos mínimos necesarios para exportar la
D1 objetivo. Ningún valor real debe guardarse en el repositorio, POS, logs,
argumentos de comandos ni objetos de backup.

## Gate local reproducible

Desde la raíz del repositorio:

```bash
cd tools/cloudflare-lab
npm ci --no-audit --no-fund
cd ../..
node --test tests/cloud-sync/d1-backup-workflow.test.mjs
```

El CANON Critical CI ejecuta este test automáticamente porque
`tests/cloud-sync/*.test.mjs` forma parte del gate y
`tools/cloudflare-backup/**` está incluido en sus filtros de rutas.

## OWNER_ONLY — cierre operacional H12/H40

No declarar rollback/backup operacionalmente verificado hasta completar todos
estos pasos con credenciales reales y evidencia retenida:

1. crear/verificar el bucket privado `nuevo-amanecer-prod-v2-backups`;
2. provisionar los tres secretos del Workflow sin exponerlos;
3. desplegar exclusivamente `tools/cloudflare-backup/wrangler.jsonc`;
4. ejecutar un export real controlado y obtener manifest `PASS`;
5. verificar objeto SQL, tamaño, SHA-256, database ID y bookmark;
6. crear una D1 temporal de recovery, distinta de producción y de LAB;
7. importar allí el SQL verificado;
8. ejecutar `PRAGMA foreign_key_check`, checks de schema/triggers, control CANON,
   conteos y reconciliación financiera;
9. conservar evidencia del drill antes de eliminar la D1 temporal;
10. mantener producción en modo conocido/read-only hasta que el gate de activación
    CANON sea autorizado por separado.

Un restore contra la D1 de producción requiere autorización de incidente, ventana
operativa y un backup/bookmark fresco. Nunca es una acción automática de este Workflow.
