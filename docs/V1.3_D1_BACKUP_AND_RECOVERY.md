D1 Time Travel is always enabled on the production storage backend. It is the
first recovery layer and retains point-in-time history for the plan's retention
window. The second layer is the daily Workflow in `tools/cloudflare-backup/`,
scheduled at `08:00 UTC` (`03:00 Peru`). Each successful run stores an SQL dump
and a JSON manifest in R2. Export temporarily blocks D1 requests, so it remains
scheduled outside business hours.

## Cloudflare configuration

Create the private R2 bucket `nuevo-amanecer-prod-v2-backups`. Configure
`ACCOUNT_ID`, `DATABASE_ID` and `D1_REST_API_TOKEN` as encrypted Worker secrets;
the API token must have only the permissions needed to export this D1. Never put
these values in Git, the POS, browser storage, logs, command arguments, or backup
objects. Deploy only `tools/cloudflare-backup/wrangler.jsonc` after the local gate
passes. The backup Worker has no public trigger; its fetch handler always returns
404.

Use the installed Wrangler from `tools/cloudflare-lab` on Windows:

```powershell
npx.cmd wrangler secret put ACCOUNT_ID --config ../cloudflare-backup/wrangler.jsonc
npx.cmd wrangler secret put DATABASE_ID --config ../cloudflare-backup/wrangler.jsonc
npx.cmd wrangler secret put D1_REST_API_TOKEN --config ../cloudflare-backup/wrangler.jsonc
```

## Backup gate

Run before every deploy and before every migration:

1. Confirm branch, HEAD and `git status --short`; do not discard local work.
2. Confirm D1 metadata with `npx.cmd wrangler d1 info nuevo-amanecer-prod-v2 --json`.
3. Capture the current Time Travel bookmark with `npx.cmd wrangler d1 time-travel info nuevo-amanecer-prod-v2 --json`.
4. Trigger a dedicated Workflow instance through the Cloudflare dashboard or Workflows API and label the operator record `PRE-DEPLOY` or `PRE-MIGRATION`.
5. Wait for Workflow state `complete` and manifest `status: PASS`.
6. Verify the R2 SQL object's size and `sha256` custom metadata match the manifest, and retain the object key plus bookmark in the deployment record.
7. Abort the deploy/migration if any value is missing, the export is stale, or the Workflow is not `complete`. Never substitute an older daily backup silently.

The export API returns `at_bookmark`; the Workflow records it as `bookmark`.
Every manifest also records timestamp, exact database ID, SQL object key, byte
size, SHA-256 and status. Failed runs write a `FAIL` manifest without claiming an
SQL object.

If R2 itself is unavailable, even the FAIL manifest may be impossible to write;
the errored Workflow instance is authoritative and blocks the gate. The current
implementation fails closed above 16 MiB per SQL export; implement streaming or
multipart storage before growth reaches this limit. Workflow retries and platform
restart semantics still require a deployed isolated test. A compiled Worker and
mocked API/R2 tests do not prove a scheduled backup exists.

## Recovery drill and restoration

Never test restore against production. Use a new temporary D1 database explicitly
named as a recovery lab and isolated credentials.

1. Freeze all writers and preserve the incident time, current production bookmark, affected operation IDs and R2 manifest.
2. Prefer Time Travel when the required point is within retention. Resolve the timestamp to a bookmark, but do not run `time-travel restore` on production during a drill; that command overwrites the target in place.
3. For the long-term layer, download the selected R2 SQL object in an operator-controlled temporary directory and verify its byte size and SHA-256 against the manifest before reading or importing it.
4. Create a new temporary D1 recovery database. Never reuse either production database or `nuevo-amanecer-lab`.
5. Import the verified SQL into that temporary database using the official D1 SQL import procedure.
6. Run `PRAGMA foreign_key_check`, schema/trigger checks, canonical control checks, promotion digest checks and count/amount reconciliation. Confirm financial no-delete triggers are present.
7. Exercise only synthetic read/retry/recovery cases against the temporary Worker binding. Do not replay historical imports or real operations.
8. Record PASS/FAIL, temporary database ID, source manifest/hash/bookmark and observed reconciliation. Delete the temporary lab only after its evidence is retained and explicit approval is given.
9. A real production restore requires a separate incident authorization, an outage window and a fresh pre-restore export/bookmark. It is never an automatic Workflow action.
