# V1.3 A5 - Staging, migracion reproducible y reconciliacion

## Estado base

- Rama: `feature/v1.3-mobile-cloud`.
- Base exacta: `f43b6f850052ea17afd1dca5113e37919963dcb2`.
- A2-A4 se preservan; A5 no hace deploy, cutover ni inicia A6.
- `evidence/v1.3/` y las fuentes comerciales privadas quedan fuera del commit.

## Objetivo y frontera de seguridad

A5 congela, valida, normaliza y carga datos comerciales en staging D1 de forma
reproducible. Produce un reporte `PASS` o `FAIL` con conteos, montos, duplicados,
huerfanos y diferencias. No promociona staging a las tablas comerciales A3 porque
el esquema 0004 no representa clientes, creditos, pagos, gastos ni cierres sin
perder informacion. Esa frontera evita convertir A5 en un cutover implicito.

El unico writer sigue siendo el Worker autenticado por A2. El migrador local no
accede directamente a D1: en `--stage` envia lotes a
`POST /commands/import.stage`. `--dry-run` no usa red ni modifica D1.

## Fuentes admitidas

1. Respaldo POS JSON envuelto `nuevo-amanecer-pos-backup` o snapshot directo V8/V9,
   con `data`. Si el wrapper declara integridad SHA-256 sobre `payload-json`, debe
   coincidir con `SHA-256(JSON.stringify(payload))`.
2. XLSX con una o mas hojas llamadas `Clientes`, `Creditos` y `Pagos` o `Abonos`.
   Los encabezados se normalizan sin tildes y sin depender de mayusculas.

El XLSX no completa campos ausentes. En particular, un abono sin fecha se guarda
como `fecha: null` y `fecha_conocida: false`; nunca se usa la fecha actual, la del
credito ni la fecha del archivo.

Las fuentes privadas se colocan solo en
`tools/cloudflare-lab/private/a5-inputs/`, ruta ignorada por Git. El `.gitkeep` es
el unico archivo versionado de ese directorio.

## Identidad, hashes e idempotencia

- `import_id` es estable y lo asigna el operador; un retry debe reutilizarlo.
- `source_hash` resume el manifiesto ordenado de archivos con nombre, tipo, bytes y
  SHA-256 de los bytes originales.
- `payload_hash` es SHA-256 del JSON canonico de cada fila.
- `manifest_hash` resume las identidades y hashes de todas las filas ordenadas.
- `transform_version` es `a5-v2-date-fidelity` y congela estas reglas.
- Mismo `import_id` y hashes devuelve el estado existente.
- Mismo `import_id` y contenido distinto responde `409 import_id_conflict`.
- La unicidad fuente/version impide cargar silenciosamente el mismo conjunto con
  otro identificador.

No se editan filas manualmente. Una correccion exige generar un archivo fuente
nuevo, conservar ambos hashes y ejecutar un `import_id` nuevo.

El fix PRE-A6 de serializacion no modifica las fuentes: conserva cada `Date`
valido como string ISO mediante `toISOString()` y rechaza `Date` invalido.
Requiere un nuevo `import_id`; los runs `a5-v1` y `a5-v1-a4-quarantine-v1`
se conservan, pero no equivalen a los corregidos ni se reparan en sitio.

## Esquema 0005

- `import_runs`: identidad, hashes, version del transformador, writer, estado,
  conteos y reporte completo.
- `import_staging`: fila normalizada, ubicacion en la fuente, payload canonico,
  hash y estado `VALID` o `REVIEW`.
- `import_issues`: diferencias y errores preservados de forma estructurada.

Estados de run: `STAGING`, `PASS`, `FAIL`. `PASS` significa que staging coincide
con el manifiesto y no hay incidencias. No significa que exista cutover.

## Validacion y reconciliacion

El migrador rechaza esquema/version desconocidos, entidades sin ID estable,
importes invalidos y relaciones no interpretables. En pagos, una fecha presente
pero invalida se rechaza y una fecha ausente se conserva como desconocida.
La reconciliacion calcula:

- conteos por entidad;
- montos de creditos, pagos, saldos y ventas;
- claves duplicadas por tipo;
- creditos sin cliente;
- pagos sin credito;
- diferencia entre pagos detallados y `pagado` declarado;
- diferencia entre `monto - pagado` y `saldo` declarado.

Los hallazgos no se corrigen ni se descartan: quedan en `import_issues` y el run
termina `FAIL`. El Worker reconstruye desde staging el hash del origen y manifiesto,
los conteos, montos, duplicados, huerfanos y diferencias; solo finaliza si todo
coincide exactamente con el reporte enviado.

## Uso local

Instalar dependencias una vez dentro de `tools/cloudflare-lab`:

```powershell
npm.cmd install
```

Dry-run, sin red:

```powershell
node tools/cloudflare-lab/scripts/a5-migrate.mjs --import-id a5-2026-09-19 --json tools/cloudflare-lab/private/a5-inputs/respaldo.json --xlsx tools/cloudflare-lab/private/a5-inputs/clientes-creditos.xlsx --dry-run --output tools/cloudflare-lab/private/a5-inputs/reporte-a5.json
```

La opcion explicita `--quarantine-a4-tests` excluye solo las ventas de prueba A4
`V-001` y `V-002`, sus movimientos relacionados por `ventaId`/`referenceId` y
revierte su efecto de stock despues de validar `stockAntes`, deltas y continuidad.
Sin esta opcion no se aplica ninguna exclusion. El reporte conserva fuentes y
SHA-256 originales y agrega la seccion auditable `report.exclusions`.
La ejecucion usa `transform_version=a5-v2-date-fidelity-a4-quarantine-v1` para no confundirse
con un run del mismo origen sin cuarentena. La politica falla de forma cerrada si
el SHA-256 del JSON no coincide con el respaldo A4 expresamente autorizado.

Carga a staging local o a un entorno no productivo expresamente elegido:

```powershell
$env:DEVICE_ID='writer-provisionado'
$env:SYNC_TOKEN='credencial-no-versionada'
node tools/cloudflare-lab/scripts/a5-migrate.mjs --import-id a5-2026-09-19 --json tools/cloudflare-lab/private/a5-inputs/respaldo.json --xlsx tools/cloudflare-lab/private/a5-inputs/clientes-creditos.xlsx --stage --endpoint http://127.0.0.1:8787
```

No ejecutar `migrate:remote`, `deploy` ni apuntar `--endpoint` a produccion como
parte de A5. El operador debe revisar el reporte completo, incluidos los `FAIL`.
